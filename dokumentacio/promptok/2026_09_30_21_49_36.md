Igen, **az észrevételeid jogosak**. A korábbi értékelésemben három különböző dolgot mostam össze: mi nincs tárolva, mi származtatott adat, és mi valódi eltérés.

- **Egyedi tevékenység:** ha létrehozásakor bekerül a `fejlesztesi_eszkozok` táblába egy cél alá, majd a foglalkozáshoz kapcsolódik, a jelenlegi séma kezeli. A `FELADAT.md` „ad-hoc órai téma” megfogalmazását érdemes ehhez igazítani, mert az szabad szöveg későbbi hozzárendelését is sugallhatja.
- **Másolható KRÉTA órai munka:** ha mindig a kiválasztott eszközök nevéből áll elő, nem kell tárolni.
- **Foglalkozásszám:** itt tényleg a `FELADAT.md` pontatlan. Az „óraszámban” szót cserélném „foglalkozásszámban”-ra. Egy apró logikai pontosítás: a célhoz tartozó eszközök megvalósulásainak *összege* nem feltétlenül azonos a különálló foglalkozások számával. Ha egy alkalmon két eszközt használtál ugyanahhoz a célhoz, az összeg 2, a foglalkozások száma 1. Érdemes eldönteni, melyiket akarod megjeleníteni.

**A fizetés viszont valóban hiányzik a sémából.** Mivel a felületen egyszerre több gyermek PDF-je is kiválasztható, én egy megrendelés + megrendelési tételek modellt választanék. Egy Stripe Checkout-fizetés így több, darabonként árazott PDF-et is fedezhet.

Az alábbi DBML-részletet a `SEMA.md` végére lehetne illeszteni kiindulásként:

```text
// ==========================================
// PDF MEGRENDELÉSEK ÉS FIZETÉS
// ==========================================

Enum dokumentum_tipus {
  fejlesztesi_terv
  szoveges_ertekeles
}

Enum megrendeles_allapot {
  letrehozva
  fizetesre_var
  fizetve
  sikertelen
  visszateritve
}

Table pdf_megrendelesek {
  id int [pk, increment]
  fejleszto_id int [not null]
  dokumentum_tipus dokumentum_tipus [not null]
  allapot megrendeles_allapot [not null, default: 'letrehozva']
  osszeg_kisebb_egysegben int [not null, note: 'Pl. HUF esetén forintban']
  penznem char(3) [not null, default: 'HUF']
  stripe_checkout_session_id nvarchar(255) [null]
  stripe_payment_intent_id nvarchar(255) [null]
  letrehozva datetime2 [not null, default: `sysdatetime()`]
  fizetve datetime2 [null]

  indexes {
    fejleszto_id [name: 'idx_pdf_megrendelesek_fejleszto']
    stripe_checkout_session_id [unique, name: 'uq_stripe_checkout_session']
    stripe_payment_intent_id [unique, name: 'uq_stripe_payment_intent']
  }
}

Ref: fejlesztopedagogusok.id < pdf_megrendelesek.fejleszto_id

Table pdf_megrendeles_tetelek {
  id int [pk, increment]
  megrendeles_id int [not null]
  tanev_gyermek_id int [not null]
  egysegar_kisebb_egysegben int [not null]

  indexes {
    megrendeles_id [name: 'idx_pdf_tetelek_megrendeles']
    (megrendeles_id, tanev_gyermek_id) [unique, name: 'uq_pdf_tetel_gyermek']
  }
}

Ref: pdf_megrendelesek.id < pdf_megrendeles_tetelek.megrendeles_id
Ref: tanev_gyermekek.id < pdf_megrendeles_tetelek.tanev_gyermek_id
```

**A hozzá tartozó legfontosabb működési szabályok:**

1. Megrendeléskor a backend ellenőrzi, hogy minden kiválasztott `tanev_gyermek_id` a bejelentkezett pedagógushoz tartozik, és **a szerver számolja ki az árat**.
2. A Stripe Checkout Session az adott megrendeléshez kapcsolódik. Stripe metadata mezőbe legfeljebb a belső megrendelésazonosító kerüljön, **gyermek neve vagy más érzékeny adat ne**.
3. A megrendelés csak a **Stripe aláírásának ellenőrzése után, webhook alapján** válik fizetetté. A böngésző visszairányítása vagy a frontend által küldött „sikeres fizetés” nem elég.
4. A PDF endpoint ellenőrzi a pedagógust, a megrendelési tételt és a fizetett állapotot. A webhook ismételt kézbesítése nem adhat duplán jogosultságot.
5. Dönteni kell, hogy a fizetés **melyik dokumentumverzióra** vonatkozik. Ha a tervet fizetés után átírják, az új PDF ingyen letölthető legyen, vagy új fizetés kell? Prototípushoz egyszerű szabály lehet: *a fizetés az adott gyermek adott tanévi dokumentumának letöltésére jogosít, későbbi módosítás után is*. Ha ténylegesen „egy konkrét PDF-példányért” fizetnek, akkor verziózás vagy biztonságosan tárolt, változatlan PDF is szükséges.

Egy technikai megjegyzés: **SQL Serverben a nullable Stripe-azonosítók egyedi indexeit a migrációban szűrt egyedi indexként** érdemes létrehozni (`WHERE ... IS NOT NULL`). A fenti DBML ezt a részletet nem fejezi ki pontosan.

Az ütemterv **11.30.** pontján a `FizetesService` mellé külön felírnám a *Stripe-webhook kezelése és ellenőrzése*, valamint a *PDF-letöltési jogosultság tesztelése* feladatokat.
