A megérzésed az RLS-ről és a mély JOIN-okról **teljesen helytálló**. SQL Serveren (T-SQL) a Row-Level Security egy inline table-valued function-ön (TVF) és Security Policy-n alapul. Ha egy predicate függvényben 3–4 táblán át kell JOIN-olni (pl. `SESSION_CONTEXT(N'UserId')` vagy `fejleszto_id` eléréséhez), az MSSQL optimizer **minden egyes lekérdezésnél** beágyazza ezeket a JOIN-okat. Ez drasztikusan rontja az execution plant és könnyen tesztelhetetlenné válik.

Az ilyen multi-tenant / pedagógus-szintű izolációknál a bevált MSSQL gyakorlat a **kontrollált denormalizáció**: a `fejleszto_id` közvetlenül szerepeljen minden olyan operatív táblában, amire közvetlen lekérdezést futtat az alkalmazás.

---

### Kritikus logikai hibák és MSSQL sajátosságok az eredeti sémában

1. **Elgépelt FK referencia:**
* Eredeti: `Ref: fejlesztesi_teruletek.id <? fejlesztesi_terv_sorok.fejlesztesi_eszkoz_id`
* Hiba: A mező neve `fejlesztesi_eszkoz_id`, de a `fejlesztesi_teruletek` táblára mutatott a `fejlesztesi_eszkozok` helyett.


2. **Hiányzó FK kapcsolat:**
* A `gyermekek.iskola_id` mezőre nem volt definiálva `Ref` az `iskolak.id`-ra.


3. **MSSQL adattípusok:**
* `varchar` hossz nélkül MSSQL-ben alapértelmezetten 1 vagy 30 karakter, ami adatvesztést/hibát okoz. Mindig kötelező a méret: `nvarchar(100)`, `nvarchar(255)`.
* Ékezetes magyar nevekhez és szövegekhez **`nvarchar`** kötelező (`varchar` helyett).
* A `timestamp` MSSQL-ben egy bináris verziószám (`rowversion`), NEM időbélyeg! Időpont tárolására a **`datetime2`** használandó.
* Az `Enum` típust az MSSQL nem ismeri natívan; DBML-ben maradhat, de DDL exportnál `nvarchar(20)` + `CHECK CONSTRAINT` lesz belőle.


4. **Ciklikus függőség (`fejlesztopedagogusok` ↔ `tanevek`):**
* A `fejlesztopedagogusok.aktiv_tanev_id` hivatkozik a `tanevek`-re, a `tanevek.fejleszto_id` pedig a fejlesztőre. Ezt az FK-t létrehozáskor külön `ALTER TABLE`-lel kell felvenni, és engedni kell a `null` értéket.


5. **Dátumformátumok:**
* `felulvizsgalat_ideje` eredetileg `varchar` volt. Érdemes `date`-re vagy `nvarchar(20)`-ra venni, ha strukturált dátum.

### Hogyan működik az MSSQL RLS ezzel a sémával?

Amikor az alkalmazás kapcsolatot nyit a DB felé, beállítja az aktuális felhasználó `fejleszto_id`-ját:

```sql
EXEC sp_set_session_context @key = N'FejlesztoId', @value = @CurrentFejlesztoId;

```

A biztonsági szűrőfüggvény így JOIN-mentes, egyszerű feltétel marad minden fő táblán:

```sql
CREATE FUNCTION Security.fn_FejlesztoSecurityPredicate(@FejlesztoId INT)
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN (
    SELECT 1 AS fn_result
    WHERE @FejlesztoId = CAST(SESSION_CONTEXT(N'FejlesztoId') AS INT)
);

```

Ez a megoldás minimális tárhely-redundanciával jár, cserébe az indexeket optimálisan tudja használni a motor, és kizárja a több szintű JOIN-okból fakadó szivárgásokat és lassulásokat.

1. **Kezdőévek tárolása:** Mind a `tanevek`-nél, mind a `szakvelemenyek.felulvizsgalat_kezdo_ev`-nél `smallint` tárolja a kezdőévet (pl. `2025` jelöli a 2025/2026-os tanévet). Ezzel a rendezés, szűrés és a felülvizsgálatok kalkulációja aritmetikailag pontos és gyors.

### Mi változott a kapcsolatok felépítésében?

* **Kétirányú kapcsolat a szakvéleményeknél:** A `gyermekek.id < szakvelemenyek.gyermek_id` biztosítja, hogy a gyermekhez korlátlan számú szakvélemény tartozhat történeti jelleggel. A `szakvelemenyek.id - gyermekek.aktiv_szv_id` pedig azonnali, O(1) elérést biztosít az épp érvényben lévő szakvéleményhez anélkül, hogy a tanévenkénti beiratkozási táblát terhelné.
* **Egyszerűbb tanévváltás:** Amikor egy új tanév indul, a diákok átmásolása a `tanev_gyermekek` táblába mindössze a `gyermek_id` és a léptetett `osztaly` (pl. 2.a $\to$ 3.a) beszúrását jelenti. Nem kell szakvélemény-hivatkozásokat újraellenőrizni vagy sokszorosítani.
